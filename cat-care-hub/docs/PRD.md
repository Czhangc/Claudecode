| 项目 | 内容 |
|---|---|
| 版本 | v0.1（2026-10-29） |
| 负责人 | cccc |

---

## 1. 问题陈述

城市室内养猫人获取养猫知识的主要渠道是小红书、抖音等社交媒体，信息碎片化，来源不明，经常互相矛盾。主人很难判断"这条建议能不能信"、"我家猫现在的状态算不算正常"、"这个症状要不要马上去医院"。

后果有两类：一是长期小问题被忽视，例如超重、喂食量凭感觉、环境让猫有压力；二是急症被耽误，例如公猫尿闭、误食毒物。前者影响寿命和生活质量，后者可能致命。

## 2. 目标用户

**主要用户（v1）：cccc 本人和咪宝。** 第一版先服务好一个真实用户，用真实使用来验证。

**次要用户（后续）：小红书上的城市养猫人。**
- 养 1–3 只室内猫，多数已绝育
- 愿意花时间研究养猫，但没有兽医背景
- 痛点是"不知道该信谁"，不是"找不到信息"

## 3. 目标

| # | 目标 | 衡量方式 |
|---|---|---|
| G1 | 新用户能在 3 分钟内完成建档 + 体况评分，并拿到每日建议喂食克数 | 首次使用计时（自测 + 3 位朋友试用） |
| G2 | 界面上 100% 的健康建议都附有来源，且标明核对状态 | `validate:content` 通过；人工抽查 |
| G3 | 主人形成记录习惯：连续 4 周每周至少记录 1 次体重 | 本地数据统计 |
| G4 | 急症信息触达足够快：从首页到"必须马上就医"清单 ≤ 1 次点击 | 走查 |
| G5 | 每个阶段上线后能产出至少 1 篇可发布的内容 | 账号发布记录 |

## 4. 非目标

| 不做什么 | 原因 |
|---|---|
| 诊断疾病、替代兽医 | 风险不可控；产品定位是分诊和日常管理 |
| 任何用药或剂量建议 | 同上，且涉及法规风险 |
| 用 AI 从照片自动判断疼痛或情绪 | Feline Grimace Scale 是为人工观察急性疼痛设计和验证的；自动识别的准确性无法保证，误判代价高 |
| 有疾病的猫、幼猫、怀孕/哺乳猫的热量计算 | 需要个体化方案，交给兽医 |
| 账号系统、云同步、多设备 | v1 是本地工具；增加隐私和运维负担 |
| 狗和其他宠物 | 聚焦 |

## 5. 分期计划

| 阶段 | 主题 | 核心交付 | 对应内容选题（账号） |
|---|---|---|---|
| **Phase 0** | 地基 | 脚手架、内容 schema、校验脚本、免责声明、急症速查页 | "我让 AI 只说有出处的话" |
| **Phase 1（MVP）** | 体型 + 饮食 | 猫咪档案、体重记录、体况评分向导、喂食计算器 | "我家猫到底该吃多少克？" |
| **Phase 2** | 互动 + 行为 | 环境五大支柱自查、行为信号图鉴、互动记录 | "你家是猫友好环境吗？" |
| **Phase 3** | 症状分诊 | 规则驱动的分诊流程、疼痛面部观察、症状日志 | "这些情况别等，马上去医院" |
| **Phase 4** | AI 知识问答 | 只基于已核对知识库回答，必须带引用 | "一个不会乱说的 AI 猫咪顾问" |

每个阶段独立可用、独立上线。前一阶段的 P0 全部完成后才进入下一阶段。

## 6. 需求明细

优先级：**P0** = 没有就不能上线；**P1** = 很快跟进；**P2** = 未来考虑，但现在的设计要为它留空间。

每个功能的视觉和交互形式见 `DESIGN_SPEC.md` 第 6 节；实现符合该节描述，也是验收标准的一部分。

### Phase 0 — 地基

**F0.1 免责声明与首次引导（P0）**
- 用户故事：作为新用户，我想在开始前知道这个工具能做什么、不能做什么，这样我不会把它当成兽医。
- 验收标准：
  - [ ] 首次打开时显示简短说明：本工具用于日常管理和就医分诊，不能诊断疾病，紧急情况请直接联系兽医
  - [ ] 用户点击"我知道了"后才进入首页，之后不再弹出
  - [ ] 每个结果页底部都有一行固定的免责文字

**F0.2 急症速查页（P0）**
- 用户故事：作为主人，我想一眼看到哪些情况必须马上去医院，这样遇到紧急情况时不用到处搜索。
- 验收标准：
  - [ ] 首页顶部有醒目入口，一次点击到达
  - [ ] 列出 `KNOWLEDGE_SOURCES.md` 中已核对的急症红线，每条附来源
  - [ ] 页面离线可用（P1 PWA 完成后）
  - [ ] 不包含任何"在家先观察看看"之类的弱化措辞

**F0.3 知识条目 schema 与校验（P0）**
- 验收标准：
  - [ ] `content/` 下每个条目都符合 `TECH_SPEC.md` 第 5 节的 schema
  - [ ] 缺少来源的条目会让 `npm run build` 失败
  - [ ] `draft` 条目在界面上显示"待核对"标记

### Phase 1 — 体型 + 饮食（MVP）

**F1.1 猫咪档案（P0）**
- 用户故事：作为主人，我想给猫建一个档案，这样所有计算都基于它的真实情况。
- 字段：名字、出生日期（或估算年龄）、性别、是否绝育、活动水平（偏少 / 正常）、是否有已知健康问题（是 / 否）、头像（可选，仅存本地）
- 验收标准：
  - [ ] Given 用户填写完必填字段，When 点击保存，Then 档案存入本地数据库并跳转到猫咪主页
  - [ ] 年龄 < 1 岁、或"有已知健康问题"为"是"时，档案页显示提示：饮食方案请由兽医制定；喂食计算器对这只猫不输出数字
  - [ ] 支持多只猫（P1），v1 至少支持 1 只

**F1.2 体重记录与趋势（P0）**
- 用户故事：作为主人，我想记录体重并看到变化趋势，这样我能及早发现体重异常。
- 验收标准：
  - [ ] 可添加日期 + 体重（kg，两位小数）
  - [ ] 体重输入超出 1–15 kg 时提示"请确认数值"，但仍允许保存
  - [ ] 折线图显示最近 12 周趋势
  - [ ] 处于减重计划时，按周计算体重变化率：
    - 每周下降 > 2%：红色警示"减得太快，有脂肪肝风险，请联系兽医"
    - 每周下降 0.5%–2%：绿色"在安全范围内"
    - 连续 4 周下降 < 0.5%：灰色提示"进展较慢，可以和兽医讨论调整方案"
  - [ ] 不在减重计划中、但体重持续下降时的提醒阈值：**待核对**（见第 9 节）

**F1.3 体况评分向导（P0）**
- 用户故事：作为没有兽医背景的主人，我想通过几个简单问题判断猫的胖瘦，这样不用只靠体重数字猜。
- 验收标准：
  - [ ] 3 个问题：摸肋骨、从上方看腰线、从侧面看腹部，每题配原创示意图
  - [ ] 根据回答给出 1–9 分的估算分数（WSAVA 9 分制），并说明 4–5 分为理想
  - [ ] 显示官方 WSAVA 体况评分图的链接（含简体中文工具包），提示用户对照确认，允许手动调整分数
  - [ ] 评分记录带日期保存，可在猫咪主页看到历史
  - [ ] 肌肉评分（MCS）为 P1

**F1.4 每日喂食计算器（P0）**
- 用户故事：作为主人，我想知道我家猫每天该吃多少克，这样不再凭感觉或只看包装上的范围。
- 输入：当前体重、最近一次体况评分、目标（维持 / 减重）、1–3 种主粮（每种填 kcal/kg 或 kcal/罐，以及占比）
- 验收标准：
  - [ ] 按 `TECH_SPEC.md` 第 4 节公式计算：理想体重估算 → RER → 每日热量 → 零食预算 → 每种粮的克数
  - [ ] 体况评分 ≥ 6 时，默认目标切换为"减重"，并显示"开始减重前建议先请兽医检查并确认目标体重"
  - [ ] 体况评分 ≤ 3 时，不输出数字，提示"体重偏轻，请咨询兽医"
  - [ ] 零食预算单独显示：每日热量的 10% 以内
  - [ ] "看看怎么算的"展开区逐步显示公式、代入值、来源
  - [ ] 所有结果标注"估算起点，个体差异可达 ±50%，请按 2–4 周后的体重和体况调整"
  - [ ] 计算结果可保存为"当前喂食方案"，减重计划从保存之日起开始计算体重变化率

**F1.5 知识卡片（P0）**
- 用户故事：作为主人，我想在工具旁边看到相关的科学解释，这样我理解为什么要这样做。
- 验收标准：
  - [ ] 每个工具页底部有 2–4 张相关知识卡片
  - [ ] 卡片显示：用自己的话写的摘要、来源列表（可点击）、核对状态、最后核对日期

**F1.6 数据导出 / 导入（P1）**
- 一键导出全部数据为 JSON；可从 JSON 恢复

**F1.7 PWA 离线可用（P1）**

### Phase 2 — 互动 + 行为

**F2.1 环境五大支柱自查（P0）**
- 基于 AAFP/ISFM 环境需求指南的五大支柱：安全的藏身处、多处且分开摆放的关键资源、玩耍与模拟狩猎、积极稳定可预期的人猫互动、尊重猫的嗅觉
- 用户故事：作为主人，我想检查我家环境是否满足猫的基本需求，这样我能减少它的压力。
- 验收标准：
  - [ ] 每个支柱 3–5 个是 / 否问题，问题内容为知识条目（需核对）
  - [ ] 结果按支柱展示做得好的地方和可以改进的地方，每条改进建议附来源
  - [ ] 可保存每次自查结果，对比前后变化

**F2.2 行为信号图鉴（P0）**
- 耳朵、尾巴、眼睛、身体姿势的常见信号，以及"它喜欢和你互动"的信号（如慢眨眼、蹭头）
- 验收标准：
  - [ ] 每个信号一张卡片：原创示意图 + 含义 + 你可以怎么做 + 来源
  - [ ] 未核对的信号卡片显示"待核对"

**F2.3 互动记录（P1）**
- 记录每天的玩耍次数和时长、互动时猫的反应，周视图

### Phase 3 — 症状分诊

**F3.1 分诊流程（P0）**
- 用户故事：作为看到猫有异常的主人，我想快速知道要不要去医院、有多急，这样不会耽误也不会白跑。
- 验收标准：
  - [ ] 第一步永远是急症红线问题（是 / 否）；命中任意一条立即显示急诊页，流程结束
  - [ ] 未命中红线时，按身体系统选择症状（排泄、饮食、呼吸、精神状态、皮肤毛发等），再回答追问
  - [ ] 结果只有三个等级：🔴 立即就医 / 🟠 24 小时内联系兽医 / 🟢 记录并观察（附复查时间和"出现以下情况立即就医"的升级条件）
  - [ ] 规则以数据形式存放（见 `TECH_SPEC.md` 第 6 节），每条规则带来源
  - [ ] 结果页可以生成"给兽医看的摘要"（症状、开始时间、体重、饮食变化），方便就诊时出示

**F3.2 疼痛面部观察（P0）**
- 基于 Feline Grimace Scale 的 5 个面部特征：耳朵位置、眼睛眯合程度、口鼻部紧张度、胡须位置、头部位置，每项 0 / 1 / 2 分，看不清的项可跳过
- 验收标准：
  - [ ] 用自己的话描述每项的 0 / 1 / 2 状态，配原创示意图，附官方网站链接（含简体中文）
  - [ ] 得分 ≥ 4/10（或按已评项目折算 ≥ 0.4）时，提示"可能存在疼痛，建议联系兽医"
  - [ ] 明确说明：仅适用于急性疼痛，不适用于关节炎等慢性疼痛；这是辅助观察，不是诊断

**F3.3 症状日志（P1）**
- 记录症状出现时间、频率、照片，可导出给兽医

### Phase 4 — AI 知识问答（P2，需单独评审）

- 只在已核对（`verified`）的知识条目范围内回答，每个回答必须引用条目 ID
- 问题超出知识库范围时，明确说"知识库里没有，请咨询兽医"，不自由发挥
- 用户问题命中急症关键词时，先显示急诊页，再决定是否回答
- 需要后端代理保管 API Key；上线前单独写技术方案

## 7. 成功指标

**先行指标（上线后 1–2 周）**
- 首次完成"建档 → 评分 → 拿到喂食克数"的用时 ≤ 3 分钟
- 试用者中 ≥ 4/5 能说出"这个数字是怎么算出来的"

**滞后指标（上线后 1–3 个月）**
- 咪宝连续 4 周有体重记录
- 账号每个阶段至少 1 篇内容；收藏 / 点赞比作为内容价值的参考

## 8. 依赖与风险

| 风险 | 应对 |
|---|---|
| 内容错误损害可信度 | 来源分级；`draft` 标记；邀请执业兽医审核（见第 9 节） |
| 用户把分诊当诊断 | 文案规范集中管理；结果页固定免责 |
| 国内访问海外托管平台不稳定 | 上线前实测；备选国内托管 |
| 版权（官方图表） | 只链接、不复制；原创示意图 |
